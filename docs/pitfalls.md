# Pitfalls

Lessons that cost time to learn. Read before changing the area they name.

## Long database work and GitHub's job limit
- **A GitHub job stops at six hours; a database statement does not.** The search index on 6.6 million pages took over three hours on Small compute (the 1-in-11 rehearsal suggested well under one). The load job was cancelled at its limit while `create index` kept running in the database, inside a transaction only the vanished script could commit, so the finished index would have been rolled back. Work that may outlast a job goes to the database's own scheduler (pg_cron), and anything a client starts that must survive it runs outside a transaction (autocommit) (27 Oct 2026).
- **Supabase's postgres role has a two-minute statement timeout, and it is armed when the statement starts.** Lifting it with `set_config` inside a `do` block does nothing for that block: the first pg_cron job was cancelled every two minutes, exactly. The job now runs `set statement_timeout = 0;` as its own statement before the block (in one command string each statement is timed on its own).

## The search page
- **Never call the auth library inside its own `onAuthStateChange` callback.** The library waits for the callback to finish before it completes its start-up, and `getSession()` inside the callback waits for that start-up: a deadlock. It showed first as a blank page with the session lock held (the lock was held by the start-up waiting on our callback), then, with a no-op lock and a time limit, as "Could not read the saved session" on every load. The callback renders the session it is handed, in a `setTimeout`, and nothing else (27 Oct 2026; the library's documentation says the same).
- **A long run writes nothing until the end: give it a budget and progress lines.** The first full gold evaluation (27 Oct 2026) asked seven statements per answer over thousands of answers and was still running at the workflow's two-hour limit, which would have discarded everything. Scripts that loop over thousands of items print progress every few dozen, stop cleanly at a time budget below the workflow's limit, and interleave groups so a cut run still reports on each of them (`gold_eval.py --budget`, `wayback_backfill.py --budget`).

- **"No answer" is not "nothing there".** The Internet Archive's index answers slowly on busy afternoons (27 Oct 2026: two of eight companies got no answer in one run and 76 rows in the next). A query that times out must come back as None, not as an empty list, or the caller records "nothing found" and, with a checked-date stamp, does not come back for 90 days. `cdx()` returns None for a timeout and [] for an empty answer; a company with an unanswered host is not stamped.
- **The text store outgrew the runner's disk.** A GitHub runner has about 14 GB free; the full-text store passed that in October 2026 (895 parts, about 10 million pages) and the mention search, which downloaded every part before scanning, failed with "Disk quota exceeded" (28 Oct). Anything that reads the whole store works in batches and deletes each batch after use.

- **GitHub's schedule is a wish, not a time.** Scheduled runs start late, sometimes by hours, and the first schedule after a workflow file changes may not fire at all (28 and 29 Oct 2026: the 20:41 run never started, the 02:41 run started at 08:40). A job that must stay out of working hours checks the clock when it starts, not only in its cron line.
- **A cancelled load leaves a backlog nobody sees.** Every load that is cancelled or cut short (a newer run, the index build, a daytime stop) leaves pages files for the next one; on 28 Oct 2026 about 2.3 million pages (216 files) had waited for days and searches missed reports the library holds. Base health now shows the backlog every day.
- **A local test corpus does not prove speed at full size.** `search_company_count` probed company by company in 0.1 s on 300,000 synthetic pages and passed 60 s on the real 10 million (28 Oct 2026): each probe of a very common word reads that word's whole index entry again. Anything that loops over companies against the full database gets a time limit and an honest partial answer.
- **Mail scanners use up sign-in links.** Corporate mail security opens every link in an incoming email to check it. A Supabase magic link and its code share one token, so the scanner's visit makes the code invalid before the person types it (28 Oct 2026, a colleague's first sign-in). The sign-in email carries the code only.
- **The database's web interface returns at most 1,000 rows, without saying so.** Supabase's API (PostgREST) caps every list of rows, functions included, at 1,000. The search page's company list stopped in the Ps (28 Oct 2026: QAFCO and Syngenta not offered) and its CSV at 1,000 pages. Anything that can pass 1,000 rows returns one JSON value instead (`*_json` functions).
- **One script, one name per function.** JavaScript keeps only the last of two `function` declarations with the same name, without any error. The fix for the callback above named the sign-in renderer `render`, which the page already used for one search result: the app never appeared, and nothing in the console said why. `tests/test_site.py` now rejects duplicate function names in `site/index.html` and a callback that reads the session (27 Oct 2026, #109).

## The text store and GitHub's limits
- **Every job that reads the text store spends the same hourly allowance.** The store is one private repository and one token: 5,000 GitHub calls an hour across every job that uses it. Each docs file is one call, and the number of files grows every night (597 on 27 Oct 2026). Eight full-text shards each downloading all of them, while the evidence database load read the store, spent the allowance at 01:18 UTC and the night's text jobs failed together. A shard reads only the parts of its own run, and a spent allowance is waited out, not retried for two minutes. Next step if the store keeps growing: one combined index file instead of hundreds of small ones.

## Airtable
- **0 equals blank in formulas.** `{page_count} = BLANK()` is true for 0, so a failure marked with 0 stays in the queue forever. Queue on a text status field.
- **`typecast` fabricates.** A string sent to a link field with `typecast: true` creates an empty row in the linked table when nothing matches. Resolve record ids first; never send strings to link fields.
- **One record twice in one batch is a 422** that fails the whole call (the 21 Oct harvest failure, PR #27).
- **Patching rows while paging a filtered query shifts the offset**; some rows are skipped that night. Harmless when the queue is re-read the next night, wrong for one-shot jobs.
- **The 500,000-record cap counts every table.** Bulk imports and new logging tables come out of the same budget.

## Fetching and documents
- **`cryptography` is a silent pypdf dependency.** Without it AES-encrypted PDFs, most corporate PDFs, fail to parse.
- **A 200 is not a page.** Consent walls, Cloudflare challenges and JavaScript shells answer 200 with no links. A page that suddenly shows no links is suspect, not empty.
- **Extensionless documents are invisible to shape tests.** Q4 `/static-files/<uuid>`, Kentico `/getattachment/`, Liferay `.pdf/<uuid>`, `/files/<slug>`, DAM hosts (Widen, Bynder): add the pattern to `monitor_core` when a site shows documents but no links are kept.
- **Truncated downloads look like PDFs.** Check Content-Length and the `%%EOF` tail before parsing; a cut body sends pypdf into a slow recovery.
- **One transient failure must not become a permanent verdict.** A 403 from a challenge, an OpenFIGI 429, a site down for a night: retry with an attempt counter before marking blocked, none or not_pdf.

## Identity and duplicates
- **Idempotency first.** A re-insert bug combined with a scope expansion once flooded the review queue. Upsert by id before widening anything.
- **Rows without a URL are invisible to the harvester's guard.** Uploads and Source Library imports can get a URL-keyed twin; dedupe's hash signal is what catches it.
- **doc_key strips short query parameters and 32-hex path segments.** Sites that select documents with them collapse distinct documents into one.
- **A purge tombstone is forever.** A wrong duplicate decision, once purged, blocks the real document.

## Classification and years
- **"First seen" is when the robot met the file, not when the company published it.** Macy's 10-K for the year ended 31 January 2026 sat on its investor page from March; the robot first harvested it on 18 July 2026, and that became its publication date. EDGAR says filed 27 March 2026. A 10-K or 20-F on a company's own site is still an SEC filing: look it up (CIK in the address or `companies.sec_cik`, then the filing of the same period). Use first seen only when the page had been watched for two weeks and the file's own dates are not older (26 Oct 2026).
- **Two classifiers disagree on half the corpus.** Never pick one silently; measure on labels.
- **Non-English documents are not AI-typed.** The classify formula runs on English only; 30,000+ rows rely on the URL guess or nothing.
- **Years in file names are publication years.** "annual-report-2025.pdf" is usually FY2024. Use the reporting-period evidence.
- **A cited 10-K is usually the right year.** US sustainability reports, CDP answers and proxy statements cite "our Annual Report on Form 10-K for the year ended ..." for the very period they report on. Ignoring such citations broke more years than it fixed (measured 23 Oct 2026). Measure a rule before believing an anecdote.
- **The top of a cover can be a table.** "Ten Year Summary 2015 2016 ... 2024" starts with the oldest year. Three or more years in the title line are a header, not the document's year.
- **Bulk rewrites move the completeness numbers.** Run a bulk year or type rewrite only after its pull request shows the measured effect (`year_eval.py`), and read the next morning's `completeness_change` on the companies that lost a check.
- **The biggest file is usually the most important one.** Full annual and integrated reports run to 10-60 MB; Airtable's upload endpoint stops at 5 MB. Anything that needs the attachment silently skips them; read from the document's own address instead.
- **Address words shared by several types decide nothing.** "sustainability report" was listed under both Sustainability Report and Integrated Report, and a tie went to whichever type came first in the file (CLP's sustainability reports typed Integrated Report, Oct 2026). Shared tokens now weigh slightly less than exclusive ones; "form 10" matched 10-Q quarterly reports as 10-K.
- **A row is not a document until it has its file.** add_link added PDF rows the site would not let us download; they sat untyped with "being read" in add_result. Open the link first and say plainly when the file is missing.
- **AI cost scales with input length.** The cover_text cap (`COVER_CHARS`) is the lever; whitespace collapsing barely matters.

- **The sections of a split report carry the whole report's contents.** UK and South African report sections repeat the full navigation bar ("Strategic report | Governance | Financial statements") on their first pages, so the parts named there say nothing about the file in hand. Compare the contents page numbers with the file's own page count.
- **"Reasonable assurance" appears in every limited-assurance report.** The ISAE 3000 boilerplate says the procedures are "less in extent than for a reasonable assurance engagement", and every financial audit opinion obtains "reasonable assurance" about the financial statements. Read the level only near sustainability words, away from the audit and internal-control wording, and never from a sentence that compares the two levels.
- **Some PDFs give text shifted by one character.** Tokio Marine's integrated report reads "DPNQBSFEXJUI" for "compared with" (a font with an off-by-one encoding). Such pages carry no terms and no years; a fix belongs in the text extraction, not in the readers.

- **A reader that waits for the full text must only wait for types the full-text build reads.** The first sustainability_class run left about 60,000 interim reports, statutory documents and presentations blank "waiting for the full text", which `build_fulltext.py` never reads (CORE_TYPES). Check the reader's scope against CORE_TYPES whenever either changes. (Since 24 Oct 2026 the nightly build reads every type, so these documents get their full text too; a reader that decided them from first pages may read them again.)

## Strategy
- **Sitemaps add junk, not reports** (37,000 bad rows in one run). Page monitoring plus search is the reliable pair.
- **The goal is events, not URLs.** "Company published a report" is the signal; filtering belongs in the pipeline, not in a review queue.
- **A formula field can return an object, not text.** When a formula fails on a row, Airtable's API returns `{"error": "#ERROR!"}` (or `{"specialValue": "NaN"}`) instead of a string. Changing `doc_label` to read a new formula (`ai_title`, 23 Oct 2026) made some rows error and `company_coverage.py` crashed on `.split`. Reads now go through `airtable_request`, which turns such values into None; formulas that read AI fields guard with `ISERROR`. Test a formula change on the PR comparison before the nightly run.
- **An empty Airtable AI field breaks formulas that read it.** An AI field never generated (state empty) makes `{field} & ''` an error inside REGEX and LEFT, and every formula built on it shows #ERROR! (doc_label, 23 Oct 2026, visible in the analysts' synced view). Guard with `IF(ISERROR(LEN({field} & '')), '', ...)` and check the rows with an empty AI field before switching a visible formula.

## One time budget for two queues starves the second
The office-network runner had one 90-minute budget for refused files, then refused pages. On 24 Oct 2026 the 300 files took 92 minutes and no page was read, although pages unlock whole sites. Give each queue its own slice (`pc_fetch.py --page-minutes`), and check every queue in the first real run, not only the first one.

## Airtable attachment links expire after about two hours
A job that lists rows first and downloads their attachments later fails on everything it reaches after the links expire. `ocr_covers.py` read 600 rows at the start of a 172-minute run on 23 Oct 2026 and 492 downloads failed. Re-read the rows in small batches just before downloading (`fresh()` in `ocr_covers.py`), or download within minutes of listing.

## Tesseract in parallel needs OMP_THREAD_LIMIT=1
Tesseract starts several threads per page by default. With 4 OCR workers on a 4-core runner they fight for the cores: on 24 Oct 2026, 22 of 25 pages hit the 120-second timeout. `ocr_covers.py` runs each tesseract with `OMP_THREAD_LIMIT=1`, so parallelism comes from the workers only.

## GitHub skips scheduled runs when it is busy
On 24 Oct 2026 the office-network workflow (cron every 4 hours) got only two of its four runs: GitHub never created the others. A job that must run often on a self-hosted runner should repeat inside one long job (`pc_fetch.py --repeat-hours 22 --every-minutes 120`) and keep the schedule only as the fallback. Cloud jobs in the nightly chain are safe because they are chained on each other (workflow_run), not scheduled one by one.

## A 200 answer is not a file
Some sites answer a request for a PDF with their home page and status 200. Airtable's own URL fetch then stores the page under the PDF's name, and the row looks attached: on 25 Oct 2026, 79 Asian Development Bank documents held the same 215 KB copy of adb.org's home page (adb-financial-report-2025.pdf, adb-sustainability-report-2024.pdf...). Build cover text marked them not_pdf, but no retry job looked at rows that already had a file. Check the attachment's type, not only its presence; `fix_wrong_attachments.py` now sends such rows back to be fetched.

## A page type is too coarse to say a gone page is covered
`sustainability_page` covers both a company's report library and a topic page about cocoa. On 25 Oct 2026 the gone-page repair unticked 307 of 317 gone pages without searching for a replacement, because the company had some other live page of the same type: Hanwha's sustainability report list (`/sustainability/reports.do`) was "covered" by an ESG topic page, FrieslandCampina's financial and sustainability reports page by whatever else was watched. A gone page that lists reports is now covered only by another live page that also lists reports (`discover_pages.is_listing`). Judge coverage by what the page holds, not by its type.

## A thread that never returns keeps the whole job alive
Every Browser monitor run from at least 16 Oct to 25 Oct 2026 ended cancelled at GitHub's 350-minute job limit, although the script stops starting pages after 180 minutes: one browser page or a Playwright thread that never returned kept the thread pool (and the Python exit) waiting. Progress was saved every 100 pages, so most of the work survived, but the runs never ended cleanly and the last pages of each were lost. Never wait on a pool without a time limit: `playwright_monitor.py` now gives each chunk at most 20 minutes, abandons hung pages to fresh workers, and ends the process with `os._exit` after the last write.

## Rolling 24-hour counts double count when a job runs twice
base_health ran at 16:41 on 25 Oct 2026 (the 12:17 schedule, started late) and again at 00:50 on 26 Oct (chained after the nightly coverage). Both counted documents created in the 24 hours before, so the 2,880 documents harvested on the morning of the 25th showed as new on both days, and the second day looked like growth that never reached the base. Count per calendar day.

## OCR with the wrong language gives noise, and noise gives wrong years
The English Tesseract model read Chinese scans as "WENS iEt imECBS {it AER GS)". The text had enough letters to count as read, the AI made a title of it, and a year rule found 2016 in it: Wen's Foodstuff lost its recent sustainability report on 26 Oct 2026. `ocr_covers.py` now adds the company's own language model and rejects output that does not read as words; covers read before are re-read with `--redo`.

## Every pull request that adds a changelog line conflicts with the next
Each pull request adds its line at the top of docs/CHANGELOG.md, so merging one leaves every other open pull request with a conflict on the same lines, and the owner waited for someone to resolve it before the next merge (26 Oct 2026). `resolve_doc_conflicts.py` now merges main into open pull requests after every merge and keeps both sides when only documentation collides. Do not resolve those by hand from a shared working folder while another job uses it: a background resolver using `git checkout -f` in the same folder discarded uncommitted work the same morning; it runs in GitHub now.

## A report quotes its predecessor's publication date (26 Oct 2026)
Bank Mandiri's 2025 Sustainability Report says it "serves as a continuation of the 2024 Sustainability Report, which was published in March 2025". The publication rule read "the ... Report ... was published in March 2025" as this report's date, and the plausibility check let it through because the row had only a year (2025), so the period end was taken as 1 January 2025. Found by the owner on the first check of 10 "publication" dates. Lessons: a sentence that names a report must name THIS edition (a year in the name older than the document's year, or "continuation of / follows / replaces" just before it, means another edition); and the floor for the date is the period the report states about itself ("for the period 1 April 2025 to 31 March 2026"), read from the text, but only a written-out span of about twelve months next to words about the report: a loose "period ... to <date>" also caught plans, comparisons, forecasts and a bond's interest period (Hua Xia Bank), and removed correct dates in the second dry run. A floor taken from the year alone does not work: tried at 31 March of the year, it removed 43 correct dates in the dry run, because many companies label a report with its publication year (a "2025" report covering 2024). Rows already written are only corrected by a re-read with `all`, because the nightly queue skips dated rows.

## A search that is fast on 600,000 pages is slow on 6,600,000 (26 Oct 2026)
The first search functions passed their checks on small phrases and failed on "scope 3", "net zero", "climate" and "World Benchmarking Alliance": statement timeout after two minutes. Three causes, all invisible at small scale: a phrase check re-reads the text of every candidate page (the index holds words, not positions); the memory for a query on the Small compute is 5 MB, so the list of candidate pages for a common word stops fitting and Postgres falls back to re-checking whole blocks of the table; and every page fetched and then dropped by a filter is a disk read on a machine whose cache holds a tenth of the table. Before changing the paid database, a 1-in-11 copy of the corpus was loaded on a local Postgres with the same memory settings (shared_buffers 512 MB, work_mem 5 MB), the problem reproduced, the new layout measured, and the migration rehearsed end to end with the loader itself. Rule: measure a search design on a real-size sample before applying it; set `work_mem` and `statement_timeout` inside the functions; and when an UPDATE touches every row of a big table, the indexes on it double in size, so build new indexes after the backfill, never before.

## A document dated next year (26 Oct 2026)
The search page listed documents from 2027 above everything else: 566 rows carried doc_year 2027, almost all from the file-name and cover rules, which accepted any year up to next year because Japanese and Indian companies label the quarter to June 2026 "FY27". The bare next year in a name is nearly always something else: a certificate "valid until 2027", notes with a "termination date of 18 October 2027", a "strategic plan for CY 2027". Rule now: next year counts only when written as a fiscal year (FY27, FY2027, 2026-27, 2026/2027, 2027年3月期). Rows already dated are never re-decided by the nightly run (it takes undated rows only), so a wrong batch needs the `redo_future` input of Document years (rules). Open question for the weekly review: a range in a name ("Annual Report 2024-25") is dated by its first year today; the Source Library labels will say which year analysts give such reports.

## A broad except hides why an outside API said no
The first model-reader check (29 Oct 2026) reported 134 failed calls and nothing else: the API's refusal was raised inside the per-answer loop, whose `except Exception` counts database timeouts, so every refusal became "database did not answer" and the reason never reached the log. A refusal a retry cannot fix (HTTP 400, 401, 403, 404: key, credit, model name) is now its own exception (`model_reader.ModelRefused`) that the loop re-raises, so the run stops and the report shows the API's message.

## A word pattern of letters only loses the labels that are numbered
Label mining first split words on letters only, so "Scope 1" and "Scope 2" both became "scope" and "tCO2e" became "tco". Labels that carry a number (scopes, categories) or a chemical formula need the digit kept: label_mining.py keeps a lone 1 to 3 and any word that mixes letters and digits, and still drops figures, years and percentages (29 Oct 2026).

## Newer models refuse sampling settings
The first model-reader call sent `temperature: 0` (the usual way to ask for a repeatable answer) and Haiku 5.5 answered HTTP 400 "`temperature` is deprecated for this model" (29 Oct 2026). model_reader.py sends no sampling settings; repeatability comes from the closed reply format and the check that the number is on the page.
## A bank's "revenue" is not its interest income
The first full Propose values run (29 Oct 2026) took `ifrs-full:RevenueFromInterest` as revenue for European banks (one large Spanish bank: 61.7 billion EUR of interest income, against 35.5 billion EUR of gross income). WBA's validated bank answers are income net of interest expense ("gross income", "total operating income"; `us-gaap:RevenuesNetOfInterestExpense` for SEC filers), and every ESEF interest-income pick differed from them (5 of 5). Interest-income concepts are out of the revenue lists; a bank gets no ESEF revenue until its net-income concept is identified, usually a company extension rather than an IFRS concept.

## A reply cut at the token limit looks like a refusal
The model reader allowed 300 output tokens. Replies averaged 236, and the model often explains before giving its JSON, so a long explanation was cut before the JSON began; the reader saw no figure and counted a decline (most of the 30 declines with the number on the page, 29 Oct 2026, had no reason because there was no JSON at all). The limit is now 1,000, the instruction says JSON only, and the report counts replies cut at the limit and names a reply with no JSON.
## A link that proves the value is not a link anyone can check it with
The first `attribute_values` rows (29 Oct 2026) pointed SEC values at the filing's folder on sec.gov: correct, but a list of twenty files (exhibits, XBRL schemas, images) with no hint of which one to open or what to look for. The analyst asked to check them could not. A source link for review must open the readable report, and the row must say what to search for in it.

## A hyphen is a different word to the word index
"location-based" and "location based" are different words to Postgres full-text search, and reports print both. The reader's labels were written with hyphens, so the pages printing "Scope 2 location based" never matched (10 of 11 missed Scope 2 location-based pages, 29 Oct 2026). Labels are now searched in both spellings, and matched on the page with either a hyphen or a space between the words.
